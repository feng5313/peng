一、费用组成与计算公式
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

费用 = 缓存命中输入tokens × 缓存命中单价 + 未命中输入tokens × 未命中单价 + 输出tokens × 输出单价

代码位置：tool_engine.py line 617-621
cost = cached_tokens × price_input_hit / 1,000,000
     + uncached_tokens × price_input_miss / 1,000,000
     + completion_tokens × price_output / 1,000,000

单价单位：元/百万tokens

当前两个已配置provider定价：

┌──────────────┬──────────┬───────────┬──────────┐
│ Provider     │ 缓存命中  │ 未命中     │ 输出      │
├──────────────┼──────────┼───────────┼──────────┤
│ z-glm5.2     │ 2        │ 8         │ 28       │
│ deepseek-pro │ 0.025    │ 3         │ 6        │
└──────────────┴──────────┴───────────┴──────────┘

二、输入输出token获取方法
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

token用量来自API返回的usage字段（client.py line 680-691），非估算。

提取逻辑（tool_engine.py line 590-611）：

1. DeepSeek格式：直接取 prompt_cache_hit_tokens / prompt_cache_miss_tokens
2. OpenAI格式：取 prompt_tokens_details.cached_tokens
3. 通用回退：尝试 cached_tokens / cache_hit_tokens 字段

提取后的分配：
- cached_tokens → _total_input_hit_tokens（缓存命中输入）
- prompt_tokens - cached_tokens → uncached_tokens → _total_input_miss_tokens（未命中输入）
- completion_tokens → _total_output_tokens（输出）
- total_tokens → _total_tokens_consumed（总消耗，独立累加）

三、出现偏差的可能性与偏差大小
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【偏差1】GLM5.2不返回缓存命中信息 — 影响最大！

GLM（智谱）API的usage只返回标准字段 prompt_tokens/completion_tokens/total_tokens，不返回 prompt_cache_hit_tokens/prompt_cache_miss_tokens（那是DeepSeek专属），也不返回 prompt_tokens_details.cached_tokens（OpenAI格式）。

结果：所有输入tokens全部计入 uncached_tokens（按未命中单价8元/百万计算），即使实际GLM后端命中了缓存。

偏差大小：
- 假设GLM实际缓存命中率约50%（连续对话前缀复用）
- 实际应计费用：50%×2 + 50%×8 = 5元/百万输入tokens
- 系统计算费用：100%×8 = 8元/百万输入tokens
- 偏差：高估约60%，即输入费用部分偏高约60%
- 对总费用影响：取决于输入/输出比，典型对话中输入token远大于输出，所以总费用可能高估30-50%

【偏差2】pricing不持久化在context中 — 低风险

_pricing字典不保存在to_context()中，也不在from_str()中恢复。每次LLM调用前由ToolEngine从provider_config重新设置（line 1609-1615）。

当前流程确保set_pricing在update_usage之前执行，所以正常流程无偏差。但如果出现异常路径（如compact/重试时provider切换后未重新set_pricing），该次调用费用计算为0（pricing为空）。

偏差大小：极低概率，偏差为单次调用费用被低估为0。

【偏差3】provider切换时定价不一致 — 设计合理

一次事务运行中可能切换provider（fallback），每次LLM调用使用当时的provider定价。这是正确行为，但意味着_total_cost是混合多个provider定价的累计值，无法精确对账到某个provider的账单。

偏差大小：非偏差，但对账困难。

【偏差4】completion_tokens包含thinking — 合理

GLM5.2的completion_tokens包含thinking内容。输出按price_output统一计费，thinking和实际输出内容不区分价格。

偏差大小：0（这是正确的，thinking也是模型生成的输出）。

四、优化方向
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【优化1】GLM5.2缓存命中检测（优先级：高）

GLM5.2 API可能支持类似OpenAI的 prompt_tokens_details 字段，或者智谱有自己的缓存机制。建议：
1. 实际抓取一次GLM5.2的完整usage响应，确认是否包含任何缓存相关字段
2. 如果GLM确实支持缓存但不报告，可以考虑按经验比例估算缓存命中（如70%），但会有精度问题
3. 更好方案：直接联系智谱确认API是否有缓存命中字段

【优化2】pricing持久化（优先级：中）

将_pricing也保存到context中，这样重启后即使set_pricing未及时执行，也能使用上次的定价，避免极端情况下的0费用计算。

【优化3】按provider分别记录费用（优先级：中）

添加 _cost_breakdown 字段，按provider分别记录费用和token用量，便于精确对账：
{"z-glm5.2": {"cost": 1.5, "tokens": {...}}, "deepseek-pro": {...}}

【优化4】费用校验机制（优先级：低）

在事务完成时，将累计费用与最后一次API返回的单次费用做合理性检查（如累计费用应≥最后一次单次费用），发现异常时发出告警。
